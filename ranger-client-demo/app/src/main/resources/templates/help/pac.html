Policy as Code란?

Ranger 화면에서 정책을 손으로 고치면 누가 언제 무엇을 바꿨는지 남지 않고, 환경(개발·운영) 사이에 옮기기도 어렵습니다. Policy as Code는 정책을 Git에 둘 수 있는 문서로 적고, 도구가 서버를 그 문서와 같게 맞추는 방식입니다.

YAML 스펙 ──parse──▶ PolicySet
                        │
   Ranger 서버 ──읽기──▶ plan  ─▶ 변경 목록 (CREATE / UPDATE / DELETE)
                        │
                      apply ─▶ 바뀐 것만 쓰기

plan과 apply

  • plan은 아무것도 바꾸지 않습니다. 양쪽을 정규화(서버가 붙인 id·버전 같은 필드 제거, 기본값 채우기, 순서 없는 목록 정렬)한 뒤 비교해 바뀔 정책·역할과 필드별 차이를 보여 줍니다.
  • apply는 다시 plan을 만들고(그 사이 서버가 바뀌었을 수 있으므로) 그 변경을 실행합니다. 역할을 먼저, 정책을 나중에 씁니다. 정책은 plan했을 때의 버전으로 고치므로, 그 사이 누가 고친 정책은 RangerConflictException으로 실패합니다.

스펙 문서의 키

키뜻
service / zone정책이 속할 서비스와 보안 영역
prunetrue면 문서에 없는 서버 정책을 지웁니다.
managed_labelprune은 이 레이블이 붙은 정책만 지웁니다. 손으로 만든 정책은 건드리지 않습니다.
roles역할(사용자·그룹 묶음)
policies정책 목록. allow/deny는 항목 목록의 줄임말입니다.

키는 snake_case(data_mask_info)와 Ranger JSON의 camelCase(dataMaskInfo)를 모두 받습니다.

이 화면 사용법

  • 편집기에서 YAML을 고치고 plan을 누르면 오른쪽에 변경 목록이 나옵니다. 필드 이름을 펼치면 변경 전·후 JSON이 보입니다.
  • apply는 실제로 Ranger를 바꿉니다. 확인 대화상자가 뜹니다.
  • Export는 서버의 정책을 스펙으로 내보냅니다. 편집기에 넣기로 바로 plan해 볼 수 있습니다.

따라 해 보기

  1. 아무것도 고치지 않고 plan: 시드가 이미 적용되어 있으므로 "서버가 이미 스펙과 같습니다"가 나옵니다(모두 NOOP).
  2. sales_read의 deny에서 mallory를 bob으로 바꾸고 plan: UPDATE 한 건과 denyPolicyItems 필드 차이가 보입니다.
  3. orders_region_filter 정책 전체를 지우고 plan: prune: true이고 레이블이 demo-seed이므로 DELETE가 나옵니다.
  4. 되돌리려면 페이지를 새로 고치세요(편집기가 시드 문서로 돌아갑니다). apply하지 않았다면 서버는 그대로입니다.
apply로 시드 정책을 바꾸면 PDP 권한 확인의 결과도 달라집니다. 원래 문서로 다시 apply하면 돌아옵니다.

이 화면이 쓰는 API

PolicyAsCode pac = new PolicyAsCode(admin);

PolicySet spec = SpecLoader.parseYaml(yaml, "editor.yaml");
// 파일·디렉터리에서: SpecLoader.load(List.of(Path.of("policies/")))

Plan plan = pac.plan(List.of(spec));        // 바꾸지 않음
System.out.println(plan.render());          // 사람이 읽는 요약
Map<Change.Action, Integer> n = plan.summary();

List<Change> applied = pac.apply(plan);     // 바뀐 것만 쓰기

String yaml = PolicyAsCode.toYaml(pac.export("demo_hive", null));
